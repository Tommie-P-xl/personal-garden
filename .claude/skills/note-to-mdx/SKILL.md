# 手稿笔记转 MDX

将粗糙的学习手稿转换为结构化、组件丰富的 MDX 笔记文件，可直接放入 personal-garden 项目中使用。

## 核心原则

**使用者提供内容要点和框架，你负责结构优化和组件编排。**

不要求使用者了解 MDX 组件细节，你来判断哪些内容适合用什么组件展示。

## 工作流程

```
输入手稿 → 分析内容 → 规划章节 → 【询问用户】→ 确认结构 → 生成 MDX
                    ↑                              │
                    └──── 用户要求修改 ←────────────┘
```

### 第一步：读取与分析

读取用户提供的笔记内容，识别：
- **核心主题**：这篇笔记讲什么？
- **知识要点**：有哪些关键概念、步骤、公式、代码？
- **逻辑关系**：要点之间是什么关系？（并列、递进、对比、包含）
- **内容类型**：每个要点属于哪种类型？（概念解释、代码示例、公式推导、对比说明、操作步骤）

<Callout type="warning">
**用户要求记录：** 在这一步，必须记录用户提出的所有额外要求（如"代码注释要详细"、"多用图表"等）。这些要求必须贯穿后续所有步骤，不可遗忘。
</Callout>

### 第二步：章节规划

根据内容逻辑组织章节结构：

| 内容特征 | 推荐结构 |
|---------|---------|
| 概念+细节 | 概述 → 分章节详解 → 总结 |
| 步骤/流程 | 简介 → 步骤1/2/3 → 注意事项 |
| 对比类 | 概述 → 对比维度 → 各方案详述 |
| 知识树 | 总览（KnowledgeMap）→ 分支详解 |

**章节顺序原则：**
1. 先总后分：先给全局视角，再深入细节
2. 先简后难：基础概念放前面，进阶内容放后面
3. 先因后果：先讲原理，再讲应用

### 第三步：确定文档组织方式

仅对新建且组织方式未确定的笔记询问单文档/多文档。若用户已指定目录结构，或要求修改、迁移现有笔记，沿用已授权结构直接实施，不重复确认。

**新建笔记且组织方式尚未确定时，先询问用户。** 已有明确结构或修改现有笔记时沿用授权。

使用 AskUserQuestion 工具向用户提问，提供以下选项：

**选项 A：单文档模式**
- 所有内容写在一个 `.mdx` 文件中
- 适合内容较少、逻辑紧凑的主题
- 示例：`0001-Git基础.mdx`

**选项 B：多文档模式**
- 内容拆分为多个 `.mdx` 文件
- 可以利用子文件夹进行分层组织（最多 3 层嵌套）
- 适合内容丰富、主题可独立拆分的笔记系列

### 第四步：多文档结构规划（仅选项 B）

如果用户选择多文档模式，需要输出详细的目录结构供用户确认：

**结构规划原则：**
- 直接相关的章节放在同一目录下作为并行的 MDX 文件
- 内容较深、需要单独展开的章节可以新建子文件夹
- 子文件夹内可以有多个并行的 MDX 文件
- 子文件夹嵌套最多 3 层（含根目录）
- 每个新目录必须有 `_meta.json`

**输出格式示例：**

```
src/content/notes/0005-git/
├── _meta.json                          ← 目录元数据
├── 0001-核心概念.mdx                   ← 基础概念（独立文件）
├── 0002-环境配置与仓库管理.mdx          ← 配置+仓库操作
├── 0003-分支管理.mdx                   ← 分支相关操作
├── 0004-暂存与提交.mdx                 ← 工作区→暂存区→版本库
├── 0005-远程操作.mdx                   ← push/pull/fetch
├── 0006-撤销与回退.mdx                 ← reset/revert/reflog
├── 0007-标签管理.mdx                   ← Tag 操作
└── 0008-GitHub-Actions/               ← 子文件夹（内容较深，独立展开）
    ├── _meta.json
    ├── 0001-基础概念与Workflow结构.mdx
    ├── 0002-触发事件与条件执行.mdx
    ├── 0003-环境变量与Secrets.mdx
    └── 0004-矩阵构建与高级用法.mdx
```

**呈现给用户时，说明：**
1. 每个文件包含哪些章节（简要概述）
2. 为什么某些内容放在子文件夹中（内容深度/独立性）
3. 文件之间的逻辑关系

对尚未获确认的新系列，等待用户确认结构；已获授权的结构直接进入下一步。

### 第五步：选择组件

根据内容类型选择最合适的组件（详见下方速查表）。

### 第六步：生成 MDX

逐个文件输出完整的 `.mdx` 内容，每个文件包含：
- 正确的 frontmatter
- 合理的章节结构
- 恰当的组件使用
- `[[双向链接]]` 关联相关笔记
- `<Progress>` 展示学习进度（如适用）

**生成过程中必须持续遵守用户提出的所有要求。** 例如：
- 用户要求"代码注释详细" → 每个代码块都必须有详细注释
- 用户要求"多用图表" → 积极使用表格、KnowledgeMap、Mermaid 等可视化组件
- 用户要求"保持简洁" → 精简文字，避免冗余说明

## 用户要求贯穿机制

<Callout type="error" title="强制规则">
用户提出的要求必须贯穿整个生成过程，不可遗忘或忽略。
</Callout>

### 要求记录

在分析阶段，提取并记录用户的所有要求：
- 内容要求（如"代码注释要详细"、"多用示例"）
- 风格要求（如"保持简洁"、"通俗易懂"）
- 格式要求（如"多用表格对比"、"加上流程图"）
- 其他特殊要求

### 要求执行

在生成每个文件时，对照检查用户要求是否已落实：

| 用户要求 | 执行方式 |
|---------|---------|
| "代码注释详细" | 每个代码块都有行内注释，解释每行/每段的作用 |
| "多用图表" | 积极使用表格、KnowledgeMap、Mermaid、对比表等可视化元素 |
| "保持简洁" | 精简文字描述，用要点列表代替长段落 |
| "加上示例" | 每个概念都配有实际示例 |
| "通俗易懂" | 使用类比、比喻，避免过多术语 |
| "对比说明" | 用表格或 Tabs 组件进行多方案对比 |

## 组件选择速查表

| 内容类型 | 推荐组件 | 使用场景 |
|---------|---------|---------|
| 重要提示/警告 | `<Callout>` | type: tip/info/warning/error |
| 定义/详细说明（可折叠） | `<Collapse>` | 不影响主流程的补充内容 |
| 多语言代码对比 | `<Tabs>` + `<TabItem>` | 同一功能的不同语言实现 |
| 数学公式 | `<Latex>` + `$$..$$` | 公式推导、数学模型 |
| 概念分类/知识树 | `<KnowledgeMap>` | 摘要卡片、多级原生折叠、命令速查 |
| 流程/状态/关系图 | `mermaid` 围栏 | 默认居中、主题同步、放大与源码查看 |
| 对比数据/属性表 | Markdown 表格 | 简单对比，自动转换样式 |
| 复杂表格（需对齐/标题） | `<Table>` | 需要 align 或 caption 时 |
| 学习进度展示 | `<Progress>` | 标记各主题完成度 |
| 图片展示 | `![](path)` 或 `<Image>` | 需要调整大小/对齐时用组件 |
| 视频/文档 | `<Media>` | 视频播放或文档下载 |
| 多图展示 | `<Gallery>` | 图片网格布局 |
| 交叉引用 | `[[笔记标题]]` | 关联其他笔记 |

## 组件使用模板

### Callout 提示框
```mdx
<Callout type="tip">
这是实用技巧。
</Callout>

<Callout type="warning">
注意事项内容。
</Callout>

<Callout type="info">
补充说明内容。
</Callout>
```

### Collapse 折叠面板
```mdx
<Collapse title="展开查看详细内容">
详细说明或代码示例。
</Collapse>
```

### Tabs 标签页
```mdx
<Tabs labels={['标签1', '标签2', '标签3']}>
<TabItem index={0} active>
第一个标签的内容。
</TabItem>
<TabItem index={1}>
第二个标签的内容。
</TabItem>
<TabItem index={2}>
第三个标签的内容。
</TabItem>
</Tabs>
```

### Latex 公式
```mdx
<!-- 块级公式（默认居中） -->
<Latex>
$$
E = mc^2
$$
</Latex>

<!-- 左对齐 -->
<Latex align="left">
$$
\sum_{i=1}^{n} i = \frac{n(n+1)}{2}
$$
</Latex>

<!-- 行内公式直接写 $...$ -->
行内公式：$a^2 + b^2 = c^2$
```

### KnowledgeMap 知识卡片（替代固定画布思维导图）

```mdx
<KnowledgeMap data={{
  name: "Git 五大区域",
  description: "先读摘要；有子项的卡片可点击或按 Enter 展开。",
  children: [
    { name: "工作区 · Working Directory", description: "编辑文件的地方", command: "git status · git diff" },
    { name: "暂存区 · Index / Stage", description: "选择下一次提交的内容", children: [
      { name: "添加修改", command: "git add <file>" },
      { name: "检查暂存", command: "git diff --cached" }
    ] }
  ]
}} />
```

`name` 必填；`description` 是始终可见的摘要；`detail` 是展开后的补充文字；`command` 放短命令；`children` 可递归。文字自动换行，手机自动单列，原生折叠无需脚本。字段内容为纯文本，不解析 Markdown。核心信息放摘要，不能只藏在折叠中。

旧 `<BraceMap data={...} />` 保留为兼容入口，渲染相同卡片；新笔记只使用 `<KnowledgeMap>`。不要再使用 `nodeWidth`、`nodeHeight`、`braceColor` 等固定画布配置。

### Mermaid 可视化（Markdown / MDX 均无需 import）

````md
```mermaid title="Git 文件状态流转"
flowchart LR
  accTitle: Git 文件状态流转
  U["未跟踪"] -->|git add| S["已暂存"]
  S -->|git commit| C["已提交"]
  C -->|编辑文件| M["已修改"]
  M -->|git add| S
```
````

- 流程用 `flowchart`；状态机可用 `stateDiagram-v2`；交互时序可用 `sequenceDiagram`；仅展示分支历史时可用 `gitGraph`。
- 默认居中；宽图在图内横向滚动，提供放大/缩小、适应窗口、Escape 关闭和源码查看。明暗主题随网站切换，不在笔记里写死颜色。
- 纵向流程优先 `TB`，短流程可用 `LR`；超过 6–8 个复杂节点时拆图。节点用稳定英文 ID，中文标签用双引号。
- 给图写 `title="..."` 和 `accTitle:`。避免 init 指令、HTML 标签、click 回调、外部图片和自定义脚本。
- 展示命令执行结果的代码块保持原样。**不得用空格、箭头、ASCII 边框拼流程图/概念树**；目录概览用 KnowledgeMap，矩阵结果用表格；实际终端输出与源代码保留。
- 按原文核对方向、条件、HEAD/分支/标签指针、前后状态，不能仅把旧图的布局机械照搬。图下保留关键解释。
- 图表在浏览器按需渲染；禁用 JavaScript、加载失败或语法错误时，保留可阅读/复制的源码。知识卡片始终可用。

### Progress 进度条
```mdx
<Progress value={80} label="主题名称" />
```

### 双向链接
```mdx
- [[相关笔记标题]] — 关联说明
```

<Callout type="error" title="重要：链接格式">
**双向链接必须使用笔记的 `title`（不含序号前缀），不是文件名！**

错误示例：`[[0001-核心概念]]`、`[[0003-暂存与提交]]`
正确示例：`[[核心概念]]`、`[[暂存与提交]]`

原因是系统会根据 `title` 来匹配笔记，使用带序号的文件名会导致链接失效。
</Callout>

## Frontmatter 规范

```yaml
---
title: 笔记标题
tags: [标签1, 标签2, 标签3]
summary: 一句话概括笔记内容（可选但推荐）
---
```

**标签命名建议：** 使用小写中文，2-4个标签为宜。

## 文件命名规范

```
src/content/notes/{分类目录}/{四位数序号}-{中文标题}.mdx
```

示例：`src/content/notes/0001-linux/0001-memory-management/0003-页面置换算法.mdx`

- 四位数序号控制同级内的排列顺序
- 渲染时自动去掉序号前缀
- 新建目录时必须同时创建 `_meta.json`

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 所有内容平铺，无组件 | 根据内容类型选择合适组件 |
| Callout 内容过长 | Callout 只放关键提示，详细内容用 Collapse |
| Tabs 用于非对比场景 | Tabs 用于同主题的多视角对比 |
| 忘记写 frontmatter | 每个 MDX 文件必须有 frontmatter |
| 新建目录不写 _meta.json | 新目录必须同时创建 _meta.json |
| 公式不用 Latex 组件包裹 | 块级公式用 `<Latex>` 包裹以控制对齐 |
| 序号格式错误 | 使用四位数：0000、0001、0013 |
| 标签过多或过少 | 2-4 个标签，覆盖主题和关键技术点 |
| **忽略用户要求** | **用户要求必须贯穿全程，每个文件都要检查** |
| **组织方式未确定就生成新系列** | **先询问单文档/多文档；已有明确授权时直接实施** |
| **双向链接使用文件名** | **双向链接必须使用笔记的 `title`（不含序号前缀），不是文件名！** |

## 完整流程示例

**用户输入：**
```
我有一份 Git 学习笔记，内容如下：
[笔记内容...]
要求：代码注释要详细
```

**第一步：分析** → 识别核心主题、知识点、逻辑关系
→ 记录用户要求：代码注释详细

**第二步：章节规划** → 规划 12 个章节

**第三步：询问用户**（必须！）

使用 AskUserQuestion：
- 选项 A：单文档（所有内容在一个文件）
- 选项 B：多文档（拆分为多个文件，可含子文件夹）

**第四步（如选 B）：输出结构** → 等待用户确认

```
src/content/notes/0005-git/
├── _meta.json
├── 0001-核心概念.mdx
├── 0002-环境配置.mdx
├── 0003-分支管理.mdx
└── 0008-GitHub-Actions/
    ├── _meta.json
    ├── 0001-基础概念.mdx
    └── 0002-高级用法.mdx
```

**第五步：生成 MDX** → 每个文件都确保代码注释详细

## 使用方式

在 Claude Code 中直接描述你的需求：

```
/note-to-mdx

我有一份关于 TCP/IP 协议的学习笔记，内容如下：
[粘贴你的笔记内容]

请帮我转换为 MDX 格式，放到 src/content/notes/0005-network/ 目录下。
要求：代码注释要详细，多用表格对比。
```

## 交付检查

1. 运行 `npm run check:content` 和 `npm run build`。
2. 对新增/修改图逐一浏览器验证渲染、节点全文、连线、明暗主题与 390px 布局，不能只检查 Mermaid 语法。
3. 图表系统修改需运行 `npm test` 与 `npm run test:integration`，覆盖双部署路径、放大关闭、导航和失败降级。
4. 更新组件指南、README 与 CHANGELOG；只有用户授权发布时才推送部署。
